# Research Report v2: Lossless Retrieval and Storage Optimization for KnowCode

**Status:** Draft  
**Date:** 2026-06-11  
**Supersedes:** `docs/research/storage_optimization_2026.md` as an implementation recommendation, without modifying the original document.

## 1. Executive Summary

The original optimization proposal correctly identifies storage duplication in KnowCode, but it overstates what binary serialization, vector quantization, and reranking can guarantee. The target objective has three hard requirements:

1. 100% accurate, lossless search and retrieval.
2. Instantaneous behavior over 50-million+ LOC codebases.
3. Only a few MB of additional storage.

Those three requirements cannot all be true for a general-purpose codebase. Exact instantaneous retrieval requires precomputed index data whose size grows with the corpus. A few-MB artifact can be useful as a manifest or routing layer, but it cannot replace an exact text/symbol index for 50M+ LOC.

The improved strategy is a tiered architecture:

| Tier | Purpose | Accuracy contract | Storage posture |
|---|---|---|---|
| Tier 0: Control manifest | Repo identity, file hashes, language/path metadata, freshness state | Exact for manifest fields | Few MB to tens of MB, depending file and symbol count |
| Tier 1: Exact code search | Literal text, substring, regex prefilter, path, symbol, language filters | 100% recall for indexed fresh files after source post-verification | Usually hundreds of MB to GB scale for 50M LOC |
| Tier 2: Structural graph | Entities, imports, references, call/inheritance edges | Best effort with confidence labels, not globally lossless | Compact relative to source but grows with symbols/edges |
| Tier 3: Semantic overlay | Natural-language discovery and ranking | Empirical Recall@K, never a lossless guarantee | Optional and budgeted |
| Tier 4: Live freshness overlay | Dirty files, edits, deletes, renames, source validation | Prevents stale answers from being presented as exact | Small plus transient update cost |

The key product decision is therefore explicit:

- If "few MB" is the hard constraint, KnowCode can provide a small freshness-aware manifest plus scan-on-demand retrieval, but not instantaneous exact global search.
- If "lossless instantaneous search" is the hard constraint, KnowCode must budget for a real exact index.
- If both are desired, ship two modes: a few-MB lite mode and a larger exact mode.

## 2. Findings from Current KnowCode Artifacts

The current design has real, fixable duplication:

- The knowledge store stores `source_code` inside each entity.
- `knowcode_index/chunks.json` stores chunk `content` and token lists.
- The original source files remain the authoritative copy on disk.
- Entity IDs embed file paths, often absolute paths.
- Vector search currently stores embeddings for chunks, while the chunk repository separately stores content.

The measured storage profile in `docs/architecture/json-storage-analysis.md` shows about 1.5 MB for `knowcode_knowledge.json` and about 5.5 MB for the semantic index on the current repository. It also shows that source appears in both the knowledge store and chunk index. Removing this duplication is worthwhile, but it is a constant-factor improvement. It does not make a 50M LOC exact index fit into a few MB.

## 3. Corrected Feasibility Model

### 3.1 What "lossless" can mean

Lossless retrieval should be scoped to mechanically verifiable operations:

- Exact file lookup.
- Exact symbol lookup for languages/symbol extractors that successfully indexed the symbol.
- Exact substring search over indexed, fresh file content.
- Exact regex search when the regex is either fully accelerated by grams or safely falls back to verified source scanning.
- Exact snippet retrieval from source bytes after content-hash validation.

Lossless should not be claimed for:

- Semantic search.
- Cross-encoder reranking.
- Static call graphs across dynamic language features.
- Approximate nearest neighbor indexes.
- Query expansion generated by an LLM.

### 3.2 Why a few MB cannot provide exact instantaneous search

An exact search engine must precompute mappings from search keys to file or chunk IDs. In code search this usually means inverted indexes over tokens, symbols, paths, and ngrams. These indexes contain postings lists, not just dictionaries. The postings dominate storage because they encode which documents contain each key.

Large production code search systems use exactly this shape. GitHub's Blackbird uses code-specific ngram indexes, path/symbol/language indexes, lazy postings iterators, sharding, compaction, and source post-verification. GitHub reports that 115 TB of code reduces to about 28 TB of unique content and an index of about 25 TB including compressed unique content. That is an excellent ratio, but it is not a few-MB artifact.

For KnowCode, a realistic local target for exact search is proportional to deduplicated source size, not a constant few MB. For 50M LOC, even a highly compressed exact index should be expected to be hundreds of MB or more, depending language mix, average line length, symbol density, gram strategy, and whether positions are stored.

## 4. Improved Architecture

### 4.1 Tier 0: Freshness-Aware Control Manifest

Keep this as small as possible. It is the only tier that should target "few MB" aggressively.

Recommended contents:

- Repository root ID and schema version.
- Relative path table with integer file IDs.
- File size, mtime, and strong content hash.
- Language and generated/vendor/test classification.
- Optional line-start offsets every N lines, not every line, for coarse seeking.
- Index generation IDs for each downstream tier.
- Dirty-file overlay state.

Do not store source text here. Do not store chunk text here. Do not store embeddings here.

Use this manifest to answer:

- Is the index fresh?
- Which files need reindexing?
- Which tier can be trusted for a query?
- Can a returned snippet be validated against the current file bytes?

### 4.2 Tier 1: Exact Text, Path, and Symbol Index

This is the correctness layer.

Recommended design:

- Use relative integer document IDs.
- Build separate indexes for:
  - file paths,
  - symbols,
  - language/facet metadata,
  - code tokens,
  - substring/regex grams.
- Use ngram or sparse-gram indexing for substring and regex prefiltering.
- Use compressed postings lists with delta encoding, bitpacking, skip data, and block-level metadata.
- Keep postings lazily readable through mmap or segment files.
- Store no source text in the index unless explicitly configured.
- Always post-verify candidate matches by reading current source bytes.

Implementation options:

1. **Zoekt adapter**  
   Best if KnowCode wants proven code-search behavior quickly. Zoekt is purpose-built for fast substring and regexp matching over source code and supports symbol-aware ranking.

2. **Tantivy-based custom exact index**  
   Best if KnowCode needs an embedded Rust search library and wants tighter control over schema and segment layout. Tantivy is Lucene-inspired and supports tokenized indexed fields plus compressed stored fields when needed.

3. **SQLite FTS5 prototype**  
   Best for a conservative Python-first implementation. FTS5 supports external-content and contentless tables, and the trigram tokenizer supports substring matching. It is not a perfect production code-search engine, but it is an excellent correctness prototype with clear persistence semantics.

The v2 recommendation is to prototype with SQLite FTS5 or Zoekt, measure, then decide whether a custom exact index is justified.

### 4.3 Tier 2: Structural Graph with Confidence

The structural graph should improve retrieval and explanation, but it should not be sold as 100% accurate across arbitrary code.

Recommended design:

- Store entities with stable integer IDs.
- Store file ID, byte range, line range, symbol name, qualified name, kind, signature hash, and source content hash.
- Store relationships with a confidence enum:
  - `exact_ast`,
  - `resolved_import`,
  - `ctags_symbol`,
  - `heuristic_name_match`,
  - `unresolved`.
- Keep unresolved references rather than forcing ambiguous links.
- Store reverse edges for traversal.
- Store edge provenance so graph answers can explain what parser or heuristic produced them.

Use graph traversal for context expansion, but verify source snippets before returning them. For dynamic languages and framework-heavy code, prefer "known callers" and "known references" wording over "all callers".

### 4.4 Tier 3: Optional Semantic Overlay

The semantic layer should be treated as recall and ranking support, not as a source of truth.

Recommended design:

- Embed symbols, declarations, docstrings, and small structural summaries first.
- Avoid embedding every overlapping chunk by default.
- Use a storage budget, such as "semantic index may not exceed 5-10% of deduplicated source size."
- Use product quantization only for optional approximate search.
- Keep exact source retrieval independent of vector results.
- Re-rank candidates only after exact/source-backed candidates have been collected.
- Track Recall@K and false-negative rates empirically.

Cross-encoders and multi-query expansion can improve ranking, but they must never be described as lossless verification. They can only score candidates that prior stages found.

### 4.5 Tier 4: Live Freshness Overlay

Freshness is part of correctness, not a performance nice-to-have.

Recommended design:

- Maintain a dirty-file table from filesystem events.
- Treat file watcher events as hints, not proof. Periodically reconcile against the Tier 0 manifest.
- On modify:
  - mark file dirty immediately,
  - rebuild exact and structural segments for that file,
  - atomically publish a new generation.
- On delete:
  - tombstone the file ID,
  - remove postings through a deletion bitmap or segment compaction.
- On rename:
  - preserve content identity through hash,
  - update path index and graph IDs atomically.
- Before returning a snippet:
  - validate current file hash or byte-range hash,
  - if stale, reindex the file or refuse exactness.

This avoids the bad state where source is fresh but search, graph, and embeddings are stale.

## 5. Storage Optimization Strategies

### 5.1 Remove source duplication first

Replace stored source text with:

- file ID,
- byte start and byte end,
- line start and line end,
- source content hash,
- optional small preview capped to a few bytes only for UI.

Chunks should become derived views. Store chunk descriptors, not chunk bodies:

```text
chunk_id -> file_id, byte_start, byte_end, entity_id, chunk_kind, token_policy_id
```

At query time, materialize the chunk from disk and validate against the source hash.

### 5.2 Intern and compress identifiers

Use:

- relative paths only,
- integer IDs for files, symbols, entities, chunks, and relationship kinds,
- string tables for path components and symbol names,
- deterministic ID assignment per index generation,
- optional content-addressed IDs for stable cross-generation mapping.

This helps portability and reduces repeated strings.

### 5.3 Use compressed postings, not JSON token arrays

`tokens: list[str]` inside JSON chunks is the wrong persistence shape at scale.

Use inverted postings:

```text
term_or_gram -> compressed list(doc_id, optional term_frequency, optional positions)
```

For exact substring search, a doc-level gram index plus source post-verification can avoid storing full positions. If phrase/proximity ranking is needed, positions can be stored only for the token index or only in selected fields.

### 5.4 Use external-content/contentless search tables for prototypes

SQLite FTS5 documents the exact tradeoff:

- normal FTS stores a private copy of content,
- contentless tables store only the full-text index,
- external-content tables retrieve content from another table but require consistency management.

For KnowCode, that maps well to a prototype:

- content lives in source files,
- FTS stores only index entries,
- Tier 0 manifest guards consistency,
- source post-verification prevents stale snippets.

### 5.5 Deduplicate by content hash

Use content-addressed blob identity:

- If two files have identical content, index content grams once and map multiple paths to the same blob ID.
- For vendored/generated code, allow opt-in indexing policies.
- For monorepos with generated artifacts, default to excluding large generated outputs unless the user explicitly opts in.

This is one of the few optimizations that can materially change large-repo economics.

### 5.6 Apply zstd where decompression is cheap

Use zstd for:

- source-free metadata blocks,
- graph edge blocks,
- string tables,
- cold segment files,
- per-language dictionaries for small metadata records.

Do not zstd-compress hot postings in a way that forces whole-block decompression for every candidate. For hot postings, prefer search-engine-native integer compression and skip structures.

### 5.7 Make vector storage budgeted and evictable

Vector storage should be optional:

- Keep an exact-only mode with zero embeddings.
- Support symbol-summary embeddings before chunk embeddings.
- Use PQ/IVFPQ only for recall acceleration, not correctness.
- Keep a full-precision rerank cache only for the hottest items if needed.
- Make semantic index deletion/rebuild independent of exact search.

## 6. Retrieval Pipeline

### 6.1 Query planning

Classify every query into one or more retrieval intents:

- `exact_text`: literal string, pasted error, identifier, config key.
- `path`: file path or path fragment.
- `symbol`: function/class/type/module lookup.
- `regex`: user-supplied pattern.
- `structural`: callers, callees, imports, inheritance, tests.
- `semantic`: natural-language concept query.

Run exact tiers before semantic tiers. This both improves correctness and reduces vector/reranker cost.

### 6.2 Exact-first execution

Recommended flow:

1. Parse the query.
2. Query path/symbol/token/gram indexes.
3. Intersect filters such as language, directory, test/vendor state.
4. Read candidate source ranges.
5. Verify exact match or regex match against current source bytes.
6. Rank verified matches.
7. Expand with graph neighbors only when useful.
8. Return minimal snippets with file, line, byte range, and validation hash.

If verification fails because the file changed, mark the file dirty and either reindex or refuse to claim exactness.

### 6.3 Semantic fallback and reranking

Use semantic retrieval only when exact retrieval has low confidence or the task is inherently conceptual.

Recommended flow:

1. Generate query embedding.
2. Search the budgeted semantic overlay.
3. Merge with exact candidates using reciprocal rank fusion or a learned ranker.
4. Rerank top candidates with a cross-encoder when configured.
5. Source-verify all returned snippets.
6. Report confidence as empirical, not guaranteed.

## 7. Target Metrics

Separate hard correctness metrics from empirical ranking metrics.

| Metric | Target |
|---|---|
| Exact substring recall on fresh indexed files | 100% after post-verification |
| Exact symbol lookup for successfully indexed symbols | 100% after source validation |
| Stale snippet return rate | 0 |
| Lite manifest storage | Few MB to tens of MB, measured by file/symbol count |
| Exact index storage | Budget as percentage of deduplicated source, not a fixed few MB |
| Exact query latency, warm cache | p95 under 200 ms for common queries on target hardware |
| Startup latency | under 50 ms before first query, using mmap/lazy readers |
| Semantic Recall@20 | Empirical target, e.g. >= 0.90 on a human-reviewed golden set |
| Semantic precision/mAP | Empirical target, never a lossless claim |
| Incremental update correctness | create/modify/delete/rename tests pass with atomic generation changes |

The most important correction is that exact storage should be budgeted as a function of deduplicated source size. A fixed few-MB exact index target should be removed unless KnowCode accepts scan-on-demand latency.

## 8. Implementation Roadmap

### Phase 0: Measurement and Contracts

1. Extend `scripts/measure_storage.py` to report:
   - source bytes,
   - unique content bytes,
   - entity count,
   - relationship count,
   - chunk count,
   - token/posting estimates,
   - vector count and projected vector sizes.
2. Add a formal retrieval contract:
   - exact modes with 100% guarantees,
   - semantic modes with empirical guarantees,
   - stale-index refusal behavior.
3. Add golden tests for exact text, symbol, regex, stale file, delete, and rename cases.

### Phase 1: Source De-Duplication and Stable IDs

1. Remove `source_code` from persisted entities by default.
2. Replace chunk `content` persistence with chunk descriptors.
3. Use relative paths and integer IDs.
4. Add file-level and range-level hashes.
5. Validate snippets against source before returning them.

### Phase 2: Exact Index Prototype

Choose one implementation path:

- SQLite FTS5 trigram/contentless prototype for quick correctness validation.
- Zoekt adapter for production-grade code search behavior.
- Tantivy prototype if embedded Rust indexing is preferred.

The prototype must support:

- path lookup,
- symbol lookup,
- exact text lookup,
- substring lookup,
- source post-verification,
- dirty-file invalidation.

### Phase 3: Structural Graph Hardening

1. Add confidence labels to relationships.
2. Preserve unresolved references.
3. Store edge provenance.
4. Add reverse indexes for callers/importers.
5. Update context expansion to avoid claiming complete dependency maps unless the parser can prove completeness.

### Phase 4: Semantic Overlay

1. Start with symbol-summary embeddings.
2. Add chunk embeddings only when evals show symbol-level retrieval is insufficient.
3. Make PQ/IVFPQ optional and budgeted.
4. Treat cross-encoder reranking as precision improvement only.
5. Report Recall@K, MRR, and false-negative examples.

### Phase 5: Binary and mmap Optimization

Only after Phase 2 and Phase 3 establish correctness:

1. Replace JSON metadata with binary segment files.
2. mmap hot read-only segments.
3. Use zstd for cold metadata blocks and string tables.
4. Add compaction for tombstones and small segments.
5. Keep migration tooling from the current JSON artifacts.

## 9. Decisions to Avoid

- Do not call vector quantization lossless.
- Do not call reranking lossless verification.
- Do not store contextual headers inside every chunk by default. Store them as derived retrieval-time features or separate compact fields.
- Do not claim static dependency traversal is 100% complete for dynamic languages.
- Do not optimize JSON structure before removing duplicated source and token arrays.
- Do not use live source reads without hash validation.
- Do not make "few MB" the exact-index budget for 50M LOC.

## 10. Recommended Product Modes

### Lite Mode

Purpose: minimal storage overhead.

- Tier 0 manifest.
- Optional small symbol/path catalog.
- No full exact index.
- Uses direct source scan for hard exact queries.
- Honest latency: not instantaneous for global search.

### Exact Mode

Purpose: lossless instantaneous local search.

- Tier 0 manifest.
- Tier 1 exact text/path/symbol index.
- Tier 4 freshness overlay.
- Optional Tier 2 graph.
- Storage budget scales with deduplicated source size.

### Intelligence Mode

Purpose: best developer-assistant experience.

- Exact Mode plus Tier 2 graph and Tier 3 semantic overlay.
- Empirical semantic quality targets.
- Cost and storage budgets configurable.

## 11. Reference Notes

The v2 recommendations are grounded in several established code-search and indexing patterns:

- GitHub Blackbird uses code-specific ngram indexes, lazy postings iterators, source post-verification, sharding, compaction, and sparse grams for large-scale code search: <https://github.blog/engineering/architecture-optimization/the-technology-behind-githubs-new-code-search/>
- Zoekt is a purpose-built trigram code search engine with substring, regexp, boolean query, and symbol-aware ranking support: <https://github.com/sourcegraph/zoekt>
- Russ Cox's explanation of regex search with trigram indexes shows why inverted postings and candidate verification are the core exact-search shape: <https://swtch.com/~rsc/regexp/regexp4.html>
- SQLite FTS5 supports trigram tokenization, external-content tables, and contentless tables, making it a useful prototype substrate for source-less exact indexing: <https://sqlite.org/fts5.html>
- Tantivy provides an embedded Lucene-inspired full-text search library with indexed/tokenized fields and compressed stored fields: <https://docs.rs/tantivy/latest/tantivy/>
- Faiss documents PQ/IVFPQ storage formulas and distinguishes exhaustive from non-exhaustive index families; these are useful for semantic overlays, not exact code retrieval guarantees: <https://github.com/facebookresearch/faiss/wiki/Faiss-indexes>
- Zstandard provides fast lossless compression and dictionary mode for small similar records, useful for metadata and cold segments: <https://facebook.github.io/zstd/>
